## [2.4.8] - 2026-10-14 <!-- HEIMDALL:PIN:FROZEN -->

The resume release. A stopped or crashed laptop client no longer unpairs the phone, and neither does Claude Code ending, restarting, resuming or sitting idle: each phone's relay login is stored outside the repo and resumed, by default with no age limit, and only an explicit disconnect, a revoke from the phone or a login the relay refuses unpairs. The push gate now grades each push against the repo being pushed, with that repo's own checks, and arms for more ways of typing a push. The SessionStart pair window sends your gh token only for a repo you ran `hmd app connect` in, and only when pairing needs it. A disk-space floor (10% free by default) stops agent spawns and test runs on a full disk. Users must re-pair phones once after upgrading. <!-- HEIMDALL:PIN:FROZEN -->

### Added
- **A repo can declare its own checks, and the push gate passes it on a record of them** — `.heimdall/repo-checks.json` (`{"schema":1,"checks":[{"name","cmd"}]}`, committed) plus `bin/heimdall-repo-checks run|status [--repo PATH]`: `run` executes each check from the repo root in order and writes `.heimdall/receipts/repo-checks.json` atomically (`head_sha`, `tree_sha`, `decl_sha256`, `dirty`, `exit_code`, `finished_at`, per-check `exit_code`/`secs`); `status` says whether it is green and current. The gate recomputes the commit, its tree and the committed declaration's hash from git objects and also requires a clean tree at run time, a green exit and exactly the declared checks; a stale, red, dirty, missing, mismatched, malformed or invalid record blocks and names the runner. A receipt attests ONE commit: the hook hands the commits the push sends as sources to `status --pushes` (each refspec's source resolved by git, HEAD for a bare push) and every one must be the receipt's `head_sha`; `--all`, `--mirror`, `--tags`, a wildcard refspec, an option it cannot read and push configuration that picks the refs (`push.default=matching`, any `remote.<name>.push`) cannot be tied to one receipt and block. The receipt's fields, types and formats are defined ONCE, in `bin/lib/hmd_repo_receipt.py`, which `run` builds the receipt with and `status` verifies it against; a test walks that definition (a receipt `run` writes passes, every field mutated alone fails). Like `last-sweep.json` it is a cooperating-agent control, not a security boundary against someone who can write the file. Test: `test/heimdall-push-gate-per-repo.test.sh`.
- **A disk-space floor: agent spawns and test runs stop below 10% free** — `HMD_MIN_FREE_PCT` (a whole percent, default 10, `0` turns it off; a value that is not a whole number from 0 to 100, such as `7%`, is the default and says so on stderr, never a silent off) is checked against the free percent (`df -Pk`, Available ÷ size) of the volume holding `TMPDIR` and of the one holding the repo; `bin/lib/hmd_disk_floor.sh` is the one definition. It is enforced in three places: the Agent hook (`bin/heimdall-precheck-agent`) denies a spawn; the Bash hook (`bin/heimdall-precheck-bash`) denies a command that RUNS a `*.test.sh` or `test/run-all.sh`, while text that only mentions one is not a run; and `test/run-all.sh` refuses to start (exit 5) beside its absolute `HMD_TEST_MIN_FREE_GB` floor (default 5; whichever is stricter refuses), then asks again before every suite and every solo re-run. Once a floor is crossed mid-sweep nothing more is launched, the suites not yet started are `REFUSED` (a table row, `suites_refused` and `disk_floor` in the receipt, and in `non_green_suites`) and the run is red (exit 1), so a sweep cut short never reads as one that passed. A hook reads its own environment, so set the knob where Claude Code runs: an inline `HMD_MIN_FREE_PCT=5 bash test/x.test.sh` reaches the test, not the hook that has already said no. A `df` that cannot answer warns and allows (a resource guard, not a security gate). `bin/heimdall-disk-floor check` shows where you stand. Test: `test/disk-floor.test.sh`.

### Changed
- `hmd app`: a stopped laptop relay client no longer unpairs the phone. Once a phone is bound, the client's relay session login (bearer
  token, hmd key, seq marks) is stored outside the repo -- the macOS Keychain (written over `security -i` stdin, never argv), else a 0600
  file under `$HEIMDALL_HOME` (`bin/lib/hmd_session_login.py`; `HMD_SESSION_LOGIN_STORE=file|keychain|auto` picks which, default auto: the Keychain on macOS when `security` is on PATH,
  else the file; `test/run-all.sh` defaults it to `file`, so a sweep never touches the operator's Keychain). A TERM, Ctrl-C, KILL or crash revokes nothing; `hmd app connect` and its
  respawns start the client with `--resume`, which reattaches to the same relay session without pairing again, however long ago the old
  client was last alive: there is no age limit unless the operator sets `HMD_SESSION_RESUME_H` (hours, per phone; `0` = never resume a stopped client's
  login), and the relay's own 30-day device-token lifetime is the one clock left. Only `hmd app disconnect`, `hmd app disconnect --device`, a revoke from the phone or a refused login unpair:
  disconnect revokes at the relay through the stored login, also for a crashed client (it used to say "could NOT be revoked"). SIGUSR1 is
  no longer a revoke trigger. No relay change, no relay deploy needed.
- `hmd app disconnect --forget-local`: the explicit way out of a stored login whose relay revoke can never be confirmed (stuck `revoking`, a relay that stays
  down or refuses it). Without the flag nothing changes -- an unconfirmed revoke still fails loudly and keeps the login -- and no other flag implies it. With it
  (all phones, or one with `--device`) the revoke is tried first; a login still unconfirmed is dropped here: the relay session id, a warning that the phone can
  keep connecting until that session expires and when (absolute UTC, the stored session expiry: the bind plus the relay's 30-day device-token lifetime) are
  printed, the stored login (Keychain item and file) is deleted under the store lock, and a `session_login_forgotten` event (`relay-events.jsonl`) and a line in
  `$HEIMDALL_HOME/logs/app.log` record session, device, expiry and that the relay was NOT told. Exit 0 only once the delete and its log succeeded. Test:
  `test/app-session-forget-local.test.sh`.
- `hmd app`: every paired phone comes back by itself after a restart, not only the first. A relay session binds one phone, so each phone has a client of its own and the
  login of its session stored; `hmd app connect` (also its supervisor's respawn, and its look every `HMD_RESUME_RECONCILE_S` seconds, default 15) and the SessionStart pair
  window now start one `heimdall-relay-client --resume-only` for every stored login that no live client serves, each resuming its own phone's session (its own seq blocks and
  store lock, no re-pair, no nonce reuse) however long ago that phone's client was last alive (an operator-set `HMD_SESSION_RESUME_H` bounds it, per phone). Phones added with
  `hmd app add-device` are included. `--resume-only` never pairs: with no login left to claim it says `resume_none` and exits 0. Test: `test/app-session-multi-resume.test.sh`.
- `hmd app disconnect` and `--forget-local` can no longer race a resume (security review of the multi-phone resume): a disconnect MARKS FIRST -- every stored login
  goes `revoking` in one hold of the store lock, before a window, the supervisor, a client or the relay is touched -- so no resume claims it afterwards (a periodic look,
  a respawn, the pair window and a `--resume-only` client all claim under that same lock and skip what is marked or gone); then the connect supervisor (its pid is
  `pid_watcher` in `connect.json`) is stopped and waited for, then the clients, and only then is the relay asked to revoke (or the login dropped), so nothing is
  left running that could reattach, respawn or look again; a connect's periodic look also stops once `connect.json` is gone. A client that got through anyway ends
  itself, revoking its session, within `HMD_SESSION_LOGIN_CHECK_S` (2 s) of its login being marked or gone; a store it merely cannot read ends nothing. Tests:
  `test/app-session-revoke-race.test.sh`.
- **A paired phone survives Claude Code ending, restarting, resuming or sitting idle** — the repo's pair window belongs to the repo, not to a session, and a paired phone is never let go of by a session ending, a restart, a resume or idle time: the SessionEnd hook leaves the window, its supervisor and the phone's client running, the supervisor brings the client back if it dies, and the next session finds the same code and the same relay session. Each repo keeps a pairing record, `$HEIMDALL_HOME/app/repos/<sha256 of the repo's real path, first 16 hex>.json` (0600: the repo's session code and the relay session and device ids of its phones; written when a phone binds, removed with the last stored login); while it exists every surface shows ITS code, so a regenerated machine seed cannot change the code of a repo with a paired phone. Only `hmd app disconnect`, a revoke from the phone or a login the relay refuses ends a pairing, and each stop of a window or a client leaves a line in `$HEIMDALL_HOME/logs/app.log` saying what ended it and whether its session was kept or revoked. `HMD_PAIR_WINDOW_IDLE_H` now defaults to 0, no idle shutdown (the window used to stop after 4 hours); set above 0 it is an operator's bound that applies only while no phone is paired. Users must re-pair phones once after upgrading: a phone paired by an earlier release has no stored login to resume (its login lived only in the running client's memory) and its repo has no opt-in record, so run `hmd app connect` in the repo; from then on a restart resumes it. Tests: `test/app-session-survives-cc-restart.test.sh`, `test/app-session-resume.test.sh`.
- **The SessionStart pair window no longer sends your gh token on its own** — it used to read `gh auth token` and register the repo's code in every attended session of every repo while `gh` was signed in, and again about every 5 minutes while no phone was paired. The token now goes out only for a repo `hmd app connect` was run for (the opt-in is a 0600 record under `$HEIMDALL_HOME/app/pair-optin/`, never inside the repo, so a checkout cannot opt itself in; `hmd app disconnect` and `hmd app connect --no-code` remove it, a session ending never does) and only when pairing needs it: the window registers the code ONCE, with the token, while no phone is paired. The relay keeps a registration 360 s and nothing renews it (no timer, no restarted client, no later session start, which finds the window open and sends nothing); a lapsed code is offered again by `hmd app connect` or `hmd app add-device`, under the same code. A repo with neither the opt-in nor a paired phone starts nothing: no `gh` call, no token, no relay request. Resuming a paired phone needs no opt-in, no `gh` and no token. `HMD_PAIR_WINDOW_RENEW=1` (exactly `1`) restores the old schedule: the code registered again about every 5 minutes, the token sent each time, until a phone binds or `HMD_PAIR_WINDOW_IDLE_H` hours pass. Tests: `test/pair-window-token-optin.test.sh`, `test/app-session-survives-cc-restart.test.sh`.
- **The push gate runs each repo's own checks, not heimdall's** — the quality gate used to run in the session's cwd for any push, so a push of the site (six gates of its own) was blocked for lacking heimdall's sweep receipt. `bin/lib/hmd_push_target.py` now names the repo each push goes to by asking git itself (`-C` chains, `--git-dir`, `GIT_DIR`, subdirectories, linked worktrees; `--work-tree` cannot act as a decoy) and its class: **sweep** (`test/run-all.sh` names `last-sweep.json`: heimdall's own regime, the old gate unchanged and fail closed, now run inside that repo), **repo-checks** (a green, current receipt of its own checks) or **unmanaged** (one warning, the push goes on). The class is read from the COMMITS a push can carry (HEAD, its upstream, `origin/HEAD`, `origin/<branch>`, the refspecs named), never the work tree, and the strictest wins: an uncommitted marker edit changes nothing, and a pushed commit that drops a marker cannot downgrade a repo whose upstream still has it. The shell is read by a conservative model (`$( )`, backticks, `eval`, `sh -c`, here-strings and heredocs fed to shells, `xargs`, `pushd`/`popd`, chains of `cd` as sets of possible states); any construct it does not model exactly (a dynamic or conditional `cd`, `cd -`, a function, `source`, `alias`, a script piped to a shell, `find -exec`, an unknown git option or subcommand, an unmodelled `GIT_*` variable, a marker that cannot be inspected) makes the command uncertain, and then EVERY repo involved gets the strict sweep gate, never a warning; a repo that declares its own checks keeps owing the receipt under uncertainty (for commits nobody can list, so it is refused until the command is restated), and a strict gate that was never evaluated (`heimdall-state` has no state there) blocks instead of allowing. Every error path is strict too: git exiting non-zero, timing out or printing something it does not print, a ref that cannot be placed, a marker that is a link, a submodule or a directory, a resolver that crashes, a corrupt or oddly typed receipt or declaration; the tests force each one (a `git` on PATH that fails, prints nonsense or hangs at each call the resolver makes). A real shell is the judge of the model: every command of a corpus is RUN by bash and zsh with a git that records where it was started, and the repositories the pushes really went to are compared with the resolver's answer. It found a `cd` behind `env`/`nice`/`xargs` (a process runs it, not this shell), the last element of a pipeline (zsh runs it in the current shell), `CDPATH=` and `command cd` (bash runs the builtin, zsh does not); the same review made `env` with any option and assignments to `HOME`, `PWD`, `OLDPWD`, `BASH_ENV` and `ENV` uncertain. The secret, self-scan, oracle and corpus stages are not relaxed. Tests: `test/heimdall-push-gate-per-repo.test.sh`, and `test/heimdall-push-gate-target-repo.test.sh` for the case that was reported (the session in heimdall, the push to another repo by `cd`, by `-C` or from it, each graded on that repo's own record).

### Fixed
- **Tests no longer fill the disk with leftover temp folders** -- on 2026-10-13 the disk reached 0 bytes free mid-session. `bin/heimdall-agents` made a `mktemp -d` work dir per call and removed it only on normal return, so the statusline's timeout kill stranded one each time (3,731 `hmd-agents.*` dirs); it now needs no on-disk work dir. `test/lib/dashboard_alerts_battery.py` never removed its dir (782 `hmd-alerts-*`). On this macOS a template-less `mktemp` ignores `TMPDIR`, so tests that set a throwaway `HOME` and ran `uv` leaked `tmp.*` dirs; the new `test/lib/private-tmp.sh` keeps a test's temp files, mktemp calls and pip/uv caches in one private root removed on EXIT, INT, TERM and HUP, adopted by `install-stranger`, `update-signed-apply` and `heimdall-deploy-maintainer`. The sweep gives each suite its own TMPDIR and removes it, records `tmp_leaks` and `tmp_outside` in the receipt, fails a suite that leaves over 50 MB inside or outside its TMPDIR, refuses to start below 5 GB free (exit 5) and refuses socket paths without headroom (exit 6). Not heimdall's and not fixed here: the `pip-unpack-*` dirs (2.2 GB), which come from Claude Code's own `~/.claude/security/agent-sdk-venv` pip bootstrap. 499 of the 534 suites (the `test/*.test.sh` files that contain `mktemp` and not `private-tmp`, counted 2026-10-15) still use bare `mktemp` and can leak if killed.
- `release/ship.sh --npm-only` and `--release-only` no longer refuse the sweep receipt a full ship has just used, and they now ship the tagged commit's own files. The ship grades the
  receipt BEFORE its version bump, so its own `chore(release): vX.Y.Z` commit (one no sweep ever saw) made that receipt look stale, and the npm-drift recovery died with "graded <the commit
  before the bump>, HEAD is <the bump>" although nothing had landed since. These two post-tag modes now grade the TAGGED commit, not HEAD: the tag `v<version>` names the release commit T,
  and the receipt covers it when it graded T itself, or the commit T was bumped from (journal and ledger commits, the hook-owned paths, aside: the rule the ship applied to that commit)
  while T does nothing but re-pin version files. That means every changed path is one the bump writes (`RELEASE_BUMP_PATHS`) or `CHANGELOG.md`, the edits are in place with file modes
  untouched, each file differs from its parent only in version numbers and sha256 digests (`CHANGELOG.md` only in the release heading), the commit has exactly one parent, its subject is
  exactly `chore(release): v<version>` and the manifest version really moved; T's own manifest must also say the version the tag is named for. Commits after the tag (journal or code) and
  uncommitted edits are irrelevant, because nothing is read from them: `--npm-only` exports `packages/` of T with `git archive` into a temporary directory (removed on exit) and publishes
  from there, so an uncommitted edit under `packages/` can no longer ship without proof (the export is checked against T's blobs, and an `export-ignore`, `export-subst` or `eol` rule that
  would change a file refuses instead); `--release-only` signs T's `install.sh` (the bytes the tag serves, which `bin/heimdall-autoupdate` verifies) instead of the working tree's, and
  refuses a `release-manifest.json` whose `install_sha256` is not T's. A `--release-only` run that must create the tag has no tagged commit to grade and still needs the receipt to cover
  HEAD, as a full ship does. A sweep recorded at a HEAD past the tag proves HEAD, not the tag, so it no longer covers the tag: the refusal names the tag's commit, the reason and the commit
  to re-sweep. The release notes are not read from T (Release prose, editable afterwards). A new full ship (it grades the commit it is about to bump), the pre-push gate and
  `bin/heimdall-state` are unchanged. Test: `test/ship-npm-only-after-bump.test.sh` (the real full ship in a throwaway repo, then the real `--npm-only` and `--release-only` with nothing
  landed in between, with a journal commit, a code commit and an uncommitted edit after the tag -- what is published and signed is compared with the tag's files -- and the shapes that must
  still be refused).
- **The per-repo push gate, last security review (2026-10-14)** -- three findings against the gate described under Changed, each with its tests in `test/heimdall-push-gate-per-repo.test.sh`
  (`test/heimdall-precheck-bash.test.sh` filters two more trace lines of the old gate's call). (1) *A resolver that cannot answer fell back to the WRONG repository.* A timeout (`HMD_PUSH_TARGET_TIMEOUT_S`),
  a crash or a missing resolver ran the strict gate on ONE directory (the hook's own cwd), so a push to another repository by `-C` / `cd`, or from the payload's cwd, went ungraded. Now the strict
  gate runs against EVERY candidate -- the session's cwd, the payload's cwd and each `-C` / `cd` / `--git-dir` / `--work-tree` directory the parser had reached (the resolver prints them itself when it times
  out or fails, without asking git; the hook adds the two cwds when it gets no answer at all) -- and the push is blocked unless all of them pass. A push whose repository git names but whose work tree cannot
  be confirmed from the other end (a dotfiles layout) is graded on those directories as well, not only on the cwd's; a gate directory the hook cannot enter blocks (it used to run the gate wherever the hook
  was). Tests C50-C53. (2) *Gate scope mismatch.* One resolved (git directory, work tree) pair now feeds classification, refspec resolution, the receipt lookup and the `heimdall-state` check: each resolver
  row carries it (`class`, work tree, extra, git directory), every git call about the pushed repository runs with `GIT_DIR` and `GIT_WORK_TREE` pinned to it, `heimdall-repo-checks status --git-dir` verifies the
  pair from both ends and reads the receipt inside that work tree, and the hook runs `heimdall-state` in that work tree with the same pair exported. A `GIT_*` variable the resolver does not reproduce
  (`GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_NAMESPACE`, `GIT_INDEX_FILE`, ...) gave the push another view of the refs than the one the gate classified; it now makes the command uncertain (transport and
  identity variables such as `GIT_SSH_COMMAND` keep the class). Tests B "pair" and B "GIT_*", C54-C59. (3) *Self-audit.* The receipt is read as ONE regular file inside the repository: a symlinked `.heimdall`,
  `.heimdall/receipts` or receipt is never followed (and `run` will not write through one), the file is opened once with `O_NOFOLLOW` and checked on that descriptor, at most 1 MiB is read (a committed
  declaration over 1 MiB is refused too) and nesting deep enough to exhaust the parser is "not valid JSON", not a crash; `status` names HEAD once and reads the tree and the declaration of that commit, so a
  HEAD that moves between its reads cannot mix two commits; one regex that backtracked quadratically on a long command (a signal cannot interrupt a regex, so the resolver's own timeout never fired) is two linear
  searches. Tests A10, B "linear time", C60-C61. The unmanaged-repo warning, the secret and self-scan gates and every earlier class rule are unchanged.
- **The push gate arms for more ways of typing a push** — the Bash hook decides whether a command is a push with one matcher (`GP_RE` in `bin/heimdall-precheck-bash`), and a push it did not read as one walked past the quality, secret, self-scan, oracle and corpus stages. It now also reads as a push: a push in backticks; behind a wrapper with its options and their values (`nice -n 5 git push`, `sudo -u user git push`, `timeout -k 5 30 git push`, `env -u NAME git push`, `ionice -c 2`, `stdbuf -oL`, `caffeinate`, `xargs -n 1`; the wrappers are sudo, doas, command, env, exec, time, timeout, nohup, nice, ionice, setsid, stdbuf, caffeinate, builtin and xargs); with a quoted or backslash-escaped command word (`"git" push`, `\git push`, `"/usr/bin/git" push`); and after an assignment or option value that holds a space, an escape or a substitution (`FOO=$(echo a b) git push`, `FOO=a\ b git push`, `git -c user.name="a b" push`, `git -C My\ Dir push`). Chains (`&&`, `;`, `||`, `|`, `&`, a newline), subshells, substitutions, `cd x &&`, `sh -c` and `eval "..."` strings, `git -C` and a full-path `git` were already read. Text that only mentions a push (`echo "git push"`, `git stash push`) still does not arm the gate. Run against the previous matcher, 17 of the 47 one-line forms in the main list of section E of `test/heimdall-push-gate-per-repo.test.sh` were not read as a push; all 47 are now. Still not armed: a push no pattern can see (`$GIT push`, unquoted `eval git push`, a here-string, a script piped into a shell, process substitution, `bash --norc -c '...'`); the native pre-push hook, where it is wired, is the only gate for those.

### Not in this release
- The kill guard is not narrowed yet (the 2.4.7 notes said 2.4.8); it still denies kills by name or computed pid. `HMD_KILL_GUARD=off` still turns it off. <!-- HEIMDALL:PIN:FROZEN -->
- `release/ship.sh` does not yet commit, check and push the site's version pins, and a full ship still publishes npm from the working tree rather than the tag; both are planned for 2.4.9.

## [2.4.7] - 2026-10-13 <!-- HEIMDALL:PIN:FROZEN -->

The second-phone release. A repo can now have more than one phone paired: `hmd app add-device` opens one extra pairing window under the same code, `hmd app status` lists each phone and `hmd app disconnect --device` revokes one, and the default stays one phone. The push gate no longer passes on lint evidence that is stale or missing, and `heimdall-stop-lint --since-push` produces that evidence for everything changed since the last push. Sweeps can be incremental, chained to the last full green run, and a guard denies kills by name after an agent's `pkill` unpaired live phones.

### Added
- **A second phone** — `hmd app add-device` opens one extra pairing window under the same code: 10 minutes by default (`HMD_ADD_DEVICE_WINDOW_S`, never above an hour), registered before the code is shown, and each use admits one phone. At most 4 phones are paired to a repo at once (`HMD_PAIR_MAX_DEVICES` lowers that, and 1 refuses `add-device`), and `--confirm` puts the new phone through the SAS compare. The default is unchanged: one phone, and the code closes once the first has paired. `hmd app status` lists each phone, and `hmd app disconnect --device <label|id>` revokes just that one (`hmd app disconnect` still ends them all): its push tokens are removed first, a revoke is final (legacy records are tombstoned), and a revoke the relay cannot confirm is reported loudly. Every phone that pairs leaves a notice in the laptop's Claude session; the name in it is the phone's own claim, so it is sanitised and quoted. A phone paired under 2.4.6 carries over into the per-phone device records (`bin/lib/hmd_devices.py`) on upgrade, without re-pairing and without a restart of its relay client. Tests: `test/app-pair-confirm.test.sh`, `test/app-upgrade-paired.test.sh`. <!-- HEIMDALL:PIN:FROZEN -->
- **Delivery receipts show tmux** — `inbox.consumer` is one of `waiting`, `tmux`, `wake` or `none`, and now says `tmux` when the armed wake is the keystroke wake of `hmd app connect --tmux` and the session's own pane is one that `connect.json`'s tmux list names; every other armed wake stays `wake`. A delivered message's `via` is one of `stop`, `prompt`, `tool`, `tmux` or `cli`: `tmux` only when the submitted prompt is the wake's fixed prompt and a queued record carries a fresh mark that the wake typed for it, `prompt` otherwise. The wake records the record ids it typed for in `inbox-wake.json`, written before the keys and taken back if they fail. All of it is read through `hmd_private_state` (link-safe, 0600 ledger). Tests: `test/heimdall-inbox-wake.test.sh`, `test/heimdall-ui-inbox.test.sh`.
- **Lint covers everything changed since the last push** — `heimdall-stop-lint --since-push` lints the diff against the push base (`@{u}`, else `origin/<branch>`, else the last full green, else every tracked file) plus uncommitted work, with the Stop path's tool selection and exclusions and the same budget (a skipped file makes the run incomplete). Its receipt records `mode`, `base_sha`, `base_ref` and `scope`, and `--list` and `--upstream-only` print the scope. Until now stop-lint linted only the edits `edit-tracker` had seen, so work merged from sub-agent worktrees had no lint evidence and the strict push gate needed an `HMD_LINT_WAIVER`. Now `heimdall-state check-quality-gates` fails a receipt that does not cover the scope (`uncovered`, naming the file and the command), and `heimdall-precheck-bash` runs the mode, bounded, when the evidence is missing, stale or uncovered, naming the exact command in its deny. The same change fixes an extensionless bash or python tool being skipped whenever a directory in its path had a dot (`.claude/worktrees`, `mktemp`'s `tmp.XXXX`): the extension test now looks at the file name only. Test: `test/heimdall-stop-lint.test.sh`.
- **Incremental sweeps, chained to the last full green run** — `test/run-all.sh --since-green` re-runs only the suites a diff since the last green FULL sweep can affect: a suite naming a changed path or the basename of a changed `bin/` script or module (the suite and its `test/lib` helpers are searched, widened through scripts that call a changed script), a changed test file, and any suite that was red in the previous run. Names match only as whole tokens and a comment-only line is not a call edge, so a script that merely mentions a changed one in a comment does not pull its suites in. The run escalates to a full sweep (`ESCALATED TO FULL SWEEP`, with `escalation_reason` in the receipt) when the diff touches test or gate infrastructure, changes more than 40 files, would select more than 20% of the suites, widens past 200 names (a hub, which selects every suite), or has a base that is older than 7 days or 200 commits, not an ancestor of HEAD, or missing; a dirty tree is refused (exit 2). `--dry-run` prints which suites would run (with `--since-green`, the selection and its reason) and runs nothing: no lock, no receipt. One sweep runs at a time: it holds an `flock` on `receipts/sweep.lock`, a second run exits 4 naming the running pid, and the kernel frees the lock if the holder dies. A suite that is red under load and green solo is reported as FLAKY-UNDER-LOAD: it counts green, because the solo re-run was always the verdict, but it is never hidden. ### Security
- **Kills by name or by a computed pid are denied** — on 2026-10-12 a sub-agent's ad hoc `pkill -f heimdall-relay-client` ended the live phone relay clients, and a client revokes its pairing on any SIGTERM, so their phones were unpaired. `bin/heimdall-precheck-bash` now reads the command like a shell (`bin/lib/hmd_kill_guard.py`) and denies `pkill`, `killall` and `skill` with any pattern; `kill` of anything but a literal pid (a variable, a substitution, an `xargs` feed, a glob, a process group, `0`, `-1`); `find -exec kill`; `fuser -k`; and those verbs run through `sh -c`, `eval` or a heredoc, generated by `awk` or `python` and piped into a shell, or typed in another letter case (`PKILL` on a case-insensitive filesystem). `kill <literal pid>`, `kill $!`, `kill -0`, reads and text that only mentions a verb stay allowed. It fails closed: a command that mentions `kill` or `fuser` and that the guard cannot fully read (an unbalanced quote or substitution, an unterminated or expanded heredoc, a verb or shell string held in a variable, nesting past 8 levels, an exception, a timeout) is denied, and the hook denies unless the guard answers `ok` with exit 0, so a crash, no output or a missing `python3` or helper all deny. It is best-effort defense in depth, not a security boundary: a text guard on shell is never complete. What would not depend on reading shell is a relay client that a stray signal cannot unpair, a client-side design that is still open. The deny now says how to turn it off, also when the guard itself failed. ## [2.4.6] - 2026-10-11 <!-- HEIMDALL:PIN:FROZEN -->

The hooks-trust release. Heimdall's hooks no longer run scripts from the repo a session happens to be in: with `CLAUDE_PLUGIN_ROOT` unset they did, so a cloned repo could run its own code on every tool call. Roots now come only from `CLAUDE_PLUGIN_ROOT` or `~/.heimdall`, and the push gate catches `git push` however it is written. A linter that fails to run is reported as a tool error instead of as findings, and `heimdall-stop-lint` works with ESLint 9.

2.4.5 was a GitHub-only release and never reached npm; take 2.4.6 instead. <!-- HEIMDALL:PIN:FROZEN -->

### Security
- **Hooks never run scripts from the session's repo** — `hooks/hooks.json` took the plugin root from `CLAUDE_PLUGIN_ROOT` or, with that unset, from the git toplevel of the current directory, so all 49 hook commands executed `bin/<script>` out of whatever repo the session was in (and `bin/lib/hook-enabled.sh` was sourced from it). A cloned repo that shipped a script under a hooked name therefore ran its code on every tool call. Every hook command now takes its root only from `CLAUDE_PLUGIN_ROOT` or the install at `~/.heimdall`, never from the working directory: no path derived from the cwd can be trusted, and a marker inside a repo is forgeable by any repo. The hook-enabled lookup and the caveman and checkpoint copy-paste snippets follow the same rule. When no root resolves, the Bash and Agent prechecks, the credential filter, the credential-read guard and the lint-config guard fail open with one `UNCHECKED` line on stderr (the gates are Heimdall's own repo policy, there is nothing of Heimdall's to run in a foreign repo, the native pre-push hook and CI stay the backstop, and failing closed would block every call), while the Write/Edit stub gate stays fail-closed. Test: `test/hooks-no-cwd-exec.test.sh` runs every hook command in a clone with a planted script for each hooked name; none of them runs.
- **The push gate catches `git push` in any form** — `bin/heimdall-precheck-bash` matched only a command line that started with `git push`, so its quality-gate check did not see `git -C <dir> push`, `cd <dir> && git push`, `make; git push`, `FOO=1 git push` or `sh -c 'git push'`. It now matches `git` as a command word after separators, env assignments, wrapper words, subshells and `sh -c`, with global options such as `-C <dir>`. Text that only mentions a push, `git stash push` and `git pushd` stay ungated. Tests: `test/heimdall-precheck-bash.test.sh` cases 17 and 25-29.

### Fixed
- **A precheck deny says why** — `bin/heimdall-precheck-bash` wrote its deny verdict to stdout and exited 2, and Claude Code shows only stderr for an exit-2 hook, so a legitimate quality-gate deny (tests not passing, lint not clean, no sweep receipt) appeared as "hook error ... No stderr output". The verdict is now stated on stderr too, as `precheck-agent` and the stub gate already did. The same change fixed a latent failure: with `CLAUDE_PLUGIN_ROOT` unset, the Bash and Agent hooks took the cwd repo as the plugin root and exited 127 on every call in any repo that is not Heimdall's; they now fail open with one stderr line (see Security).
- **stop-lint works with ESLint 9 and lints only the repo** — ESLint 9 removed the `unix` formatter, so every `eslint -f unix` call exited 2 and was counted as a lint finding: `lint_clean` flipped false (46 phantom findings in one repo) and the push gate blocked although ESLint over the whole repo was clean. `bin/heimdall-stop-lint` now reads `-f json` through `--output-file` (core in ESLint 8 and 9, and Node's stderr noise cannot corrupt the report). An ESLint that fails to run (config error, crash, missing interpreter) is a tool error, not findings: reported loudly with its own diagnostics, counted in the receipt's `tool_errors`, the run marked incomplete and `lint_clean` left as it was, a non-verdict like a timeout, because red would fake findings and green would fake evidence. It also lints only files inside `--repo`: `.claude/worktrees/`, `.heimdall/`, `node_modules/` and anything outside the repo (the Claude scratchpad, `TMPDIR`, other checkouts, `..` escapes) are dropped and the receipt records what was excluded, so stale agent worktrees no longer burn its 60 s budget. Test: `test/heimdall-stop-lint.test.sh`.
- **Biome, ruff, shellcheck and tsc failures are tool errors too** — a non-zero exit was read as findings for all of them, but the codes differ: shellcheck 2-4 and ruff 2 and 101 are failures, and biome exits 1 for findings and for a config error, so a broken config or flag showed up as phantom findings and turned `lint_clean` red. `shellcheck -f json`, `ruff --output-format json` and `biome --reporter=json` are now read from stdout (stderr kept apart); exit 1 with at least one problem in the report is a finding, counted from the report. Anything else (exit 2 or higher, a crash, a bad flag or format, an unreadable report, ruff's E902, biome's `internalError`, a missing binary or interpreter) is a tool error, handled as above. `bash -n` (exit 126 or 127), the Python `ast` check (exit 1 without a SyntaxError) and `tsc` (no file-located diagnostic) draw the same line. Tests: fake binaries per tool (clean, findings, config error, crash, bad flag, silent, missing interpreter) in both `lint_clean` states, plus the real shellcheck and ruff, in `test/heimdall-stop-lint.test.sh`.
- **The zero-footprint test no longer waits on a published release tag** — its real-`hmd` and `npx` cases ran the wrapper against the checkout's `hmd`, whose `--version` resolves from the nearest git tag. In a release's own pre-push sweep the new tag does not exist yet, so that `hmd` looked older than the pin and the wrapper fetched `install.sh` from the unpublished tag (HTTP 404): the release gate could never go green. Those cases now pin the wrapper to the version the checkout's `hmd` reports (`RUNHMD_TAG`) and hand it a tripwire installer (`RUNHMD_INSTALL_SCRIPT`) that must never be touched; the tree's own `install.sh` is served from disk, where a tampered copy is refused under the genuine digest, the genuine one is verified, and a mutant without the digest check goes red. The shipped wrapper is unchanged. Test: `test/zero-footprint.test.sh`.

### Changed
- **`--wait-quiet` is documented** — `CLAUDE.md` now says when to use the opt-in quiet gate of the full sweep: on a shared, busy machine, to start it on a settled box. The wait is relative and bounded (the 15-minute load average below `HMD_QUIET_FACTOR`, default 1.5, times the CPU count on 3 consecutive 30 s checks; it gives up after `HMD_QUIET_MAX_WAIT_S`, default 1200 s, and the sweep then runs with half the jobs and `HMD_TEST_REDUCED_PARALLELISM=1`). ## [2.4.5] - 2026-10-11 <!-- HEIMDALL:PIN:FROZEN -->

The phone-replies release. A repo now has one pairing code, the same in every session, and it stays claimable for as long as you work; what you answer or send from the phone reaches the Claude session, an answered question closes, and an idle session wakes for a message. The files hmd keeps in your repo are no longer trusted as found: they are read without following links, and the one that decides where pushes go is signed.

### Added
- **Code-only pairing** — typing the session code on a phone signed in to the same GitHub account as the laptop's `gh` pairs at once: no 6-digit number on either side, no y/N, also with `hmd app connect --bg` and with no terminal. The claim must name this laptop's own GitHub login (otherwise it is refused and nothing is revealed), no SAS is computed, shown or logged, and past that the relay is trusted to deliver the right keys. `hmd app connect --confirm` restores the compare (it needs a terminal; exit 64 without one or with `--bg`); `--no-confirm` is the default and stays accepted. A pairing leaves a notice in the Claude session's inbox and a "paired via code" note, with the device name, on the statusline.
- **One code per repo, and a pair window that outlives any one session** — the code every surface shows is the code of the REPO, not of a Claude Code session id: the per-machine seed (`$HEIMDALL_HOME/session-code.key`, 0600) plus the repo's real path, so it cannot be computed from a path or a session id and does not change from one session to the next. The statusline, `hmd ui`'s `/api/state`, `bin/lib/hmd_app_code.py`, `hmd app connect` and the pair window derive it through one function (`resolve_session_code`) and print the same five characters in every session (the statusline keys on `workspace.project_dir`, so a `cd` into a subdirectory does not change it, and a render never creates the seed). - **`hmd app connect` reuses or replaces a stale `hmd ui`** — `hmd app connect --port N` exited 6 (`hmd ui: cannot bind 127.0.0.1:N`) whenever an `hmd ui` a former connect left running still held N. It now settles the port by what holds it and reuses or replaces a stale `hmd ui` of this repo instead of failing to bind.
- **A private-state file create that raced another maker of the same name could fail** — macOS returned a spurious ENOENT to the loser about one time in eight; `hmd_private_state` now retries it.

### Security
- **Push targets come only from the paired phone, never from repo state** — `<repo>/.heimdall/app/push.json` holds the Expo token a notification is sent to, the kinds it may carry, the label in its title and the foreground flag that silences it, and it was read as found: a checked-in, planted or other-process-written file could register an attacker's token (question text and session titles then went to that device) or flip the flag to suppress or force pushes, and a link at `.heimdall/app`, `push.json` or its lock was followed and chmod'ed through. The store now believes only a record it sealed itself — HMAC-SHA256 over the whole record and the repo's real path, under the per-machine key the inbox already seals answers with, in a 0600 file reached without following a link (`bin/lib/hmd_private_state.py` for every read, write and lock, the sender's `push-sender.lock` included). **Migration:** an existing unsealed `push.json` (`"v":1`) is ignored — not read as devices, not deleted; the phone registers again at its next connect, and until then nothing is pushed. Registration itself is unchanged: only a frame that opened under the paired phone's session key reaches it.
- **State files are link-safe everywhere** — session and pairing state, the relay client's event log, rotation and status files, the inbox, the wake state and the dashboard digest state are read and written without following a link, in 0600 files, through `bin/lib/hmd_private_state.py`. A repo file can no longer choose the relay hmd talks to, a pid it signals or an identity it trusts, and a planted digest file is ignored.
- **No pairing code in the logs** — the relay client's event log no longer records the pairing code.
- **`/healthz` is locked down** — the probe `hmd app connect` uses to find a stale `hmd ui` answers only the local connect and never past the ui's auth. A first version answered before the token check on the Host header alone, which a client chooses freely, so any peer address, an exposed ui (`--allow-host`, `--trust-proxy`) or a request with proxy headers could get it.
