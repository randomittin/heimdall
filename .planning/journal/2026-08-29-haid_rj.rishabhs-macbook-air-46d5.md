The owner saw "many folks" on the statusline where only one collaborator
(ritesh7792) exists. Investigated read-only.

NOT a privacy leak. Ruled out with evidence: heimdall-presence resolves
TEAM_DIR via `git rev-parse --show-toplevel` and never falls back to
$HEIMDALL_HOME, team_id is server-derived and never client-mixed, and
every identity in every cache traces to exactly rj + ritesh7792. No third
party anywhere.

Root cause is a single-slot race, not a leak.
$HEIMDALL_HOME/ledger/status.json is MACHINE-GLOBAL and last-writer-wins
across every repo on the box, and _team_members() picks whichever of the
repo-scoped wall vs that global mirror has MORE entries. So another repo's
roster can momentarily render here. What bleeds is the SAME owner's OTHER
repo's roster -- structurally smaller than a cross-team leak, but real.
_ledger_in_scope's own docstring already names the symptom verbatim; its
fail-closed guard bounds the window without removing the race, and 60-70
concurrent worktrees on this machine is exactly what widens it.

Honest limit: the current steady state is CLEAN (roster reports 2 people,
live render shows exactly one non-self entry, ritesh7792, and the global
file currently names this repo), so this is traced from code plus the
matching docstring, NOT caught red-handed. Recorded as such.

Proposed, deliberately NOT implemented: key the global mirror per-repo so
the race is removed rather than merely detected faster. Also: 358 orphaned
.roster-cache.json.*.tmp files -- inert, but the presence writer lacks the

## 2026-08-29T02:33:00Z — [COMMUNICATION] fix(route): declare the fallback model's real context window on routed launches

Every routed launch printed "oc/big-pickle is not a model this version of
Claude Code recognizes, so auto-compact will keep this session within
200k tokens". Measured the actual value instead of guessing: the gateway's
own GET /v1/models reports oc/big-pickle.context_length = 200000, which is
EXACTLY what Claude Code was already assuming. Nothing was ever being
truncated -- the warning was a false alarm, not a symptom.

So this declares the window rather than changing it, and only from the
value the gateway itself reports. Deliberately never a hardcoded constant:
a wrong number here would cause REAL truncation instead of a cosmetic
warning, which is strictly worse than the warning. If the gateway cannot
be reached within 5s, or reports nothing usable, the variable is left
unset and the warning stands -- a noisy launch beats a fabricated context
bound. An operator's own CLAUDE_CODE_MAX_CONTEXT_TOKENS always wins.

HONEST SCOPE: this does not silence the message entirely. The
[claude-code:unrecognized_model] telemetry line still prints once, because
Claude Code still does not know the `oc/*` id. What is fixed is the window
assumption, now explicit and provably correct.

Verified end-to-end with the gate forced to ROUTE: banner shows "declared
context window 200000 (from the gateway's own /v1/models)", the routed
call returns correctly in 5s.
