## 2026-08-24T06:41:28Z — [COMMUNICATION] Merge branch 'worktree-agent-a02d0c24c1017dc40' — classify why an agent died, and bound the retry

Interrupted agents were reported for a human to resume by hand. This session showed the cost:
agents died on 'session limit resets 6pm', 'resets 11pm', 'resets 5:10am', and one on 'Prompt
is too long, automatic compaction failed' — every one needing me to notice and resume manually,
and one lost its whole task to a restart with zero commits.

The fix is classification, because the five causes need opposite handling and conflating them is
the actual danger:
  overload (529)     transient -> retry with backoff AND jitter
  quota limit        retry is useless until the reset, which is IN the error string
  network drop       transient -> retry with backoff
  context overflow   retrying identically fails identically; needs narrower scope
  real task failure  NEVER auto-retried

That last line is the one that matters. A retry loop on a genuine bug burns quota and buries the
defect, so an unknown cause does nothing and says so. Retries are bounded (attempts/max_attempts
in the cause object) — unbounded backoff against a hard outage is an infinite loop.

Reuses the reset-time parser rather than writing a second one, and keeps the existing contract
that already-committed work is never redone. Reports quota.suspected as a tri-state — true /
false / null — so 'no signal to judge from' is distinguishable from 'judged not quota', which is
the same absent-is-not-fine discipline applied everywhere else this week.

Honest limit, stated in the file: a dead agent cannot resume itself and hmd cannot see the
harness's API calls, so this classifies and makes resumption one mechanical action rather than
intercepting anything.

## 2026-08-24T17:26:13Z — [COMMUNICATION] feat(agent-resume): forward a fresh overload death to the pressure controller

An `overloaded` classification is the ONLY overload signal hmd has — it cannot
read the harness's HTTP responses — and until now it was discarded. The AIMD
spawn-pressure controller (1fad13c) had no producer, and agent-pool's consumer
(263fefa) therefore had nothing to act on. `report` now forwards an overload
death to `heimdall-pressure record --kind overloaded_error`, closing the loop:
observed 529 death -> recorded event -> reduced spawn ceiling.

EXACTLY-ONCE IS THE WHOLE DIFFICULTY. These CLIs mutate state on every
invocation — there is no side-effect-free peek — so a naive hook would record
an event per `report` call, and a third status refresh would falsely breach the
window threshold and halve concurrency off ONE real failure. The hook reuses
_resume_attempts_bump's existing RESUME-ATTEMPTS.json as its marker: it fires
only when the freshly-bumped `attempts` equals 1, so a repeat call for the same
dead agent at the same worktree HEAD sees attempts>=2 and is skipped. A genuine
new death after forward progress (a fresh commit resets attempts to 1) records
again, because that IS a new observation.

Fire-and-forget: never passes --strict, and its absence or failure can never
change this tool's exit code or its `.cause` shape. `network` is deliberately
left UNWIRED — it would need its own exactly-once marker and is out of scope.

Argument order is load-bearing: --repo is a global flag on heimdall-pressure's
top-level parser and must precede the subcommand, or argparse rejects it and
the never-fail contract swallows the failure silently. Covered by a regression
test so a future reorder cannot silently disable the hook.

test/heimdall-agent-resume-pressure.test.sh 21/21, including the falsifiers: a
repeat report records nothing (cross-checked against the ledger's own line
count, a second independent observable), a task-failure death creates no
