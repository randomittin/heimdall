## 2026-08-26T03:02:23Z — [COMMUNICATION] fix(fallback): empty the built-in ToS deny list, keep the operator override

BUILTIN_TOS_FLAGGED_PROVIDERS held ~30 entries — mistral, cohere, vertex,
nvidia, cerebras, huggingface, openrouter among them — so
target_provider_allowed could never pass for any realistic provider and the
fallback could not route AT ALL. The feature was inert, and its suite was green
because the tests used fixture names rather than real ones.

Owner decision (2026-08-26): empty it. The operator turns fallback on
EXPLICITLY — `set on|auto|switch` is a deliberate act hmd never performs itself
— and has accepted the data-handling risk. A built-in list overriding that is
hmd deciding for the operator, and here it blocked the feature entirely.

WHAT THE OLD LIST GOT WRONG: it was sourced from the 2026-08-23 assessment's
table of OmniRoute's free-tier POOLED-CREDENTIAL proxy exposure, and applied
verbatim to providers themselves. Those are different things. Using the
operator's OWN key for a direct pinned request against Mistral's first-party
API is not a ToS conflict — the credential-isolation audit specifically found
that shape to be the cleanest available.

THE MECHANISM SURVIVES, ONLY THE DEFAULT CHANGED. tos_flagged_providers in the
operator's config still denies whatever they list; proven by tests 10 and 31,
which previously relied on built-in denial and now assert the same denial via
the override. An empty target_provider still FAILS — that is a completeness
check, not policy. The keyless/weakest-terms note still prints: informing
without blocking is exactly the ask.

THIS IS NOT WHAT PROTECTED THE ANTHROPIC ACCOUNT, and the tests now prove it
rather than asserting it. New cases 46 and 47: with the deny list EMPTY and
target_provider newly allowed, a live `claude` row in OmniRoute's DB still
yields REFUSE — under `auto` and under `switch` alike. tier1_credential_absent,
anthropic_model_pinned, prefer_claude_code_flag_off and no_delegated_sidecar
are untouched and still gating; none of them ever referenced the deny-list set.

Verified end to end by hand after the carry — the first time the whole chain
has produced a route: target_provider=mistral, Tier-1 verified absent, session
verdict crossed -> VERDICT: ROUTE, exit 0.

heimdall-fallback 87/87 (was 82), bin-reachability-gate 53/53,

## 2026-08-26T03:51:48Z — [COMMUNICATION] fix(test): make the dry-run escape guard precise, not blind

The full sweep's last red suite. C3 compared ~/.heimdall's top-directory mtime
before and after a dry-run and concluded the dry-run had written to it. That
inference was sound until commit 87b5812 added the statusline rate-limit
persister: the operator's statusline runs at refreshInterval 2, so
~/.heimdall/rate-limits.json is rewritten every ~2 seconds, continuously,
bumping the directory mtime on its own. Measured independently of any test:
the dir mtime advanced across a 4-second idle window with nothing else running.

So the assertion was detecting a REAL modification and attributing it to the
wrong cause — the second time today a correct change broke a downstream
assumption (the first: the non-tty secret refusal breaking heimdall-team's
join output). Both were caught only by the full sweep, because in both cases
the changed component's own tests were green.

THE GUARD IS NOW STRONGER, NOT WEAKER, which was the requirement — a
sandbox-escape guard that stops detecting escapes is worse than a flaky one.
It performs a full-tree content check: a write to ANY file anywhere under
~/.heimdall fails C3, INCLUDING an in-place content overwrite with no rename,
which the old directory-mtime compare would have missed entirely. The three
known live writers are excluded BY EXACT PATH, never by wildcard, so a genuine
escape into a sibling file — even one sitting right next to rate-limits.json,
or inside ledger/ — still trips the gate.

PROVEN BY MUTATION, not by the absence of a failure: planting a canary file in
the real ~/.heimdall and modifying it mid-run drives the suite to 27/1; with
the canary removed it is 28/0. Verified three consecutive times, since the
2-second writer means a single green could be luck.

Left for a separate decision, not done here: rate-limits.json is volatile and
rewritten every 2s while sitting alongside stable state like verdict.json. A
cache/ subdirectory may be the better home, but bin/heimdall-session-usage and
sentinels/hmd-statusline.py both reference that path and were out of scope.

Also noticed, unrelated and pre-existing: ~/.heimdall holds
com.heimdall.dream.plist.CORRUPTED-BY-TESTRUN.20260805-1509 — real litter left
by a test run on 2026-08-05, evidence of exactly the escape class this guard
exists to catch.
