a SubagentStop hook emits a task-outcome record per spawned agent, so that instruction
was false the moment it shipped — exactly the doc-drift this repo keeps getting bitten
by, and worse than useless here because it tells the orchestrator to duplicate work the
machine now does.

baseline, and an orchestrator adds only what a hook cannot truthfully observe — the task
type, and whether acceptance criteria passed on the FIRST try at this tier. Carries the
warning that matters more than the field: never guess those values. A fabricated outcome
poisons the exact routing decision the data exists to inform, and a sparse record beats
a corrupted one.

Deliberately left intact: "nothing consumes routing-overrides.json yet, so model routing
does not adjust on its own." Verified still true — heimdall-self-improve writes it and
only it and bin/lib/dream_data.py read it; nothing in the routing decision path does.

## 2026-08-22T16:07:44Z — [COMMUNICATION] Merge branch 'worktree-agent-a8208bc33a1665c08' — fix(install): the advertised first command was dead on arrival

install.sh printed 'Next: hmd demo' and 'Run: hmd demo' BEFORE computing whether the
freshly appended PATH was live in the CURRENT shell. On a fresh install it never is —
ensure_path_on_profile writes the profile FILE for future shells and cannot mutate the
running process's PATH. So the one command a brand-new user was told to paste, printed
twice, was command-not-found in the most common case.

That is the mechanism behind the census number: 0 dispatcher invocations of hmd demo
across 384 real sessions, while install.sh advertised it as THE next step. The front
door was not cold because nobody wanted it; it was cold because it did not work.

The Run: line now bakes 'export PATH=... &&' into the printed command so it works
verbatim when pasted. The success card, a fixed-width box with no room for the export,
points at the Run: line instead of printing something dead.

Separately surfaced and NOT fixed here: a brand-new, never-logged-in user trips
heimdall-doctor-install --cc-verify first, which correctly withholds the go-ahead and
prints NOT READY. That gate works as designed; the new assertion treats it as a
legitimate outcome rather than conflating it with the PATH bug.

install-stranger 58/1. The one failure (second uninstall is not a clean no-op) is
PRE-EXISTING and reproduces on main at 56/1 — carried forward, not introduced. It is
tracked separately, not papered over.

## 2026-08-22T21:10:11Z — [COMMUNICATION] Merge branch 'worktree-agent-a7d3fb0bcb1f49157' — give the nightly dream a private TCC identity named hmd-dream

The 03:00 dream has been dead 41 days. Cause is macOS TCC: the repo sits in ~/Downloads,
a protected folder, and a LaunchAgent carries no grant. The operator's Terminal DOES hold
one, which is why manual runs always worked and misled everyone — TCC attributes a grant
to the responsible process, and launchd is not Terminal.

The old advice was to grant Full Disk Access to /bin/bash. Honest about its blast radius,
and still terrible: it authorises every bash script on the machine, forever, for one
nightly job. This replaces it with a private, ad-hoc-signed copy of bash inside
hmd-dream.app (dev.runheimdall.hmd-dream), so the grant lands on exactly one thing.

Measured, not assumed, and two findings changed the design:
- A bare copy of /bin/bash is Killed: 9 on exec. Apple platform binaries are pinned to
  their trust-cache path, so the original 'copy it, keep Apple's signature' premise was
  falsified outright.
- Ad-hoc re-signing strips that flag AND is what makes macOS display the bundle by NAME,
  which is the whole point: the operator sees a row reading hmd-dream rather than an
  opaque path they cannot attribute or revoke.

Determinism is the property that makes this safe to ship. Independent rebuilds produce a
byte-identical CDHash (verified 17bc6912... twice on this machine), so an unrelated
Heimdall update cannot silently invalidate the grant. A macOS update that changes the
source bash legitimately moves the identity — TCC works that way by design — so the
runner records the invoking interpreter and disarm now REQUIRES a confirmed identity
match rather than assuming the grant still holds. A grant that lapses in silence would be
the same self-silencing failure this whole thread exists to kill.

The plist pins the bundle explicitly instead of resolving #!/usr/bin/env bash under
launchd's minimal PATH.

Nothing here grants anything: no API can, tccutil is never invoked, the TCC database is
never touched. Detect-and-ask only, the human clicks, and disarm-on-evidence is intact —
nothing may report success until a scheduled launchd run records result=ok.

Suites green: dream-permission 83/0, dream-install-wire 40/0, dream-tcc 35/0,
dream-schedule 29/0, dream 16/0, dream-bundle 10/0.
