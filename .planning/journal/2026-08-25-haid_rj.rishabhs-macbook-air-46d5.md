pressure_control.record_event() feeds connection_reset and overloaded_error

produces, with no server involvement at all. hmd spawns up to 10 agents from

REFUTES A DOCUMENTED CEILING. bin/lib/pressure_control.py and

responses" and learns of overload only from an agent's own death message. That

session transcripts carry the API error as STRUCTURAL JSON, not prose.

Measured against this repo's own 118 transcripts: 72 records with
isApiErrorMessage=true, of which 52 are {"error":"rate_limit",
"apiErrorStatus":429} and the remainder include real
{"error":"server_error","apiErrorStatus":529} entries. isApiErrorMessage
(bool), apiErrorStatus (int|null) and error (closed string enum) are keys
Claude Code itself writes — the human-readable "API Error: 529 Overloaded"
sentence in message.content[0].text is incidental and nothing here parses it.

distinction that decided it was worth building at all.

Every record is timestamped, so the scan is windowed rather than re-reading
history: a file whose mtime predates the cutoff is skipped unopened.

DELIBERATELY READ-ONLY. It does NOT call heimdall-pressure record. Emitting a
count a caller may act on is a materially safer contract than mutating AIMD
state from a scanner that could be run twice — a double-run would otherwise
manufacture a threshold breach out of one real event. Stated in the file
header.

Never-fail contract matching heimdall-metric/heimdall-pressure: a missing
transcript dir, an unreadable file, or a malformed JSON line degrades to an
empty result at exit 0. --strict is opt-in for a bad --since.

test/heimdall-529-scan.test.sh 13/13, hermetic against constructed fixtures —

## 2026-08-25T03:20:44Z — [COMMUNICATION] feat(fallback): add heimdall-fallback, the quota-exhaustion policy gate

The owner asked for a quota-exhaustion fallback with three states: off (never),
on (fall back unattended), auto (fall back only if a preflight passes, else
wait). This is the POLICY layer only — it decides, it does not route. Transport
is deliberately not implemented here; `check`'s exit code is the seam.

  check exit 0 = ROUTE, 1 = REFUSE, 2 = WAIT

THE GATE FAILS CLOSED, AND THAT IS THE POINT. This is the one place in this
repo where refusing is safer than proceeding. `docs/analysis/2026-08-25-
omniroute-fallback-transport.md` established that OmniRoute ships no config
which verifiably disables its Tier-1 subscription cascade — the mode that
repurposes a Claude Code OAuth session as a routed backend, where enforcement
lands on the OPERATOR'S account. So `tier1_disabled` requires POSITIVE
verification and, absent it, `check` returns REFUSE even in state `on`.
Verified by hand after the carry, not just by the suite: state `on` with
Tier-1 unverified exits 1 (REFUSE), and state `auto` with a failing preflight
exits 2 (WAIT).

Six independent preflight checks — state, operator_key, endpoint_local,
endpoint_reachable, tier1_disabled, target_provider_allowed — are ALL evaluated
with no short-circuit, so a failure never hides behind an earlier one, and each
carries its own human-readable reason. "Preflight failed" with no reason is
useless at 3am when a long autonomous run has stopped.

Secrets are referenced by PRESENCE, never value: `status --json` emits
operator_key_configured (bool) and operator_key_env (a NAME), never a key.
Claude/Anthropic key names are rejected outright — the operator's own
third-party key is the only accepted credential, never the Claude session.

Defaults are safe: absent config reads `off`, and a CORRUPT config reads `off`
rather than being coerced to `on`.

test/heimdall-fallback.test.sh 22/22 including all five required falsifiers
(fresh config off, corrupt config off, on-without-Tier-1 refuses, auto-with-
failing-preflight waits, no key value in any output). Config lives at
.heimdall/fallback.json, already covered by .gitignore:46 — confirmed, so an
operator's endpoint and key-env name are never committed.

NOT WIRED YET: nothing calls `check`. Wiring waits on the transport question,
which is currently blocked. A gate that refuses is the correct thing to ship
before a route that works.

## 2026-08-25T03:44:54Z — [COMMUNICATION] feat(fallback): add heimdall-portable-brief, a scrubbed model-agnostic handoff

The owner's answer to the prompt-cache objection against provider fallback: do
not replay the conversation to a fallback model, hand it the CHECKPOINT. This
repo already writes distilled session state to .planning/CHECKPOINT.md, so the
cold start is cheap by construction — you hand over a summary rather than
paying to rebuild context on a provider with no warm cache.

THE PRIMARY RISK IS EXFILTRATION, NOT FORMATTING. A third-party provider is,
for trust purposes, public, and this repo has a standing constraint that
security-incident material stays in .planning/ and NEVER goes public. So the
scrubber FAILS CLOSED: a section it cannot confidently classify is EXCLUDED,
never included. Excluding useful context degrades a fallback answer and is
recoverable; leaking a credential is not.

IT NEVER TRANSMITS. It writes or prints a brief; a human or a separate routing
layer sends it. Keeping compose and transmit as separate steps means a bug in
the composer cannot exfiltrate on its own. Stated in the file header and in the
brief's own preamble.

Emits a manifest of what was included, scrubbed, unclassifiable, and dropped to
fit budget, so the operator can see the trade before sending anything. Output
is size-bounded (default 16000 bytes) for fallback models with smaller windows,
and names what it dropped rather than silently truncating.

VERIFIED INDEPENDENTLY, not just by its own suite: a fixture checkpoint with
planted fake credentials (an sk-ant- key, a team secret, an AWS secret) and a

THE DISTINCTION: a 429 is SELF-INFLICTED — hmd is sending too fast and recovers

## 2026-08-25T03:51:26Z — [COMMUNICATION] feat(gate-run): emit an honest machine-observed outcome record from gate verdicts

A gate's exit code is a RECORDED REAL EXIT — the same class of evidence
issue_loop.read_verdict already treats as the only trustworthy verdict source.
heimdall-gate-run now best-effort emits a heimdall-metric task record carrying
that outcome, so at least one outcome-bearing signal is machine-produced rather
than depending on an orchestrator remembering to type a command.

INSTRUMENTATION CAN NEVER AFFECT THE VERDICT. The whole block is redirected,
`|| true`d, and gated on the binaries it needs; a missing or broken
heimdall-metric leaves it a no-op. Verified directly, not just by suite: with
bin/heimdall-metric replaced by a script that exits 99, heimdall-gate-run's own
exit code is unchanged.

IT ONLY RECORDS WHAT IT CAN OBSERVE, which is the point:
  - model is always "unknown" (stored as null) — a bare git hook has no live
    model-tier signal, and a guess would poison routing evidence worse than a
    gap. heimdall-metric gains a matching carve-out: the literal "unknown"
    records null, still distinct from a typo'd tier, which is dropped as before.
  - task_type is never passed — a commit/push gate runs identically over docs,
    lint and code, so labeling any of them would be invented, not observed.
  - source is "gate-$PHASE", distinct from the hook's "subagentstop".

NO DOUBLE-COUNT, for two independent reasons: the --source tag distinguishes
them, AND structurally a null task_type can never satisfy
heimdall-self-improve's truthy filter, so a gate row cannot populate a
(task_type, model) cell at all.

FIRST-TRY SEMANTICS are keyed on the CONTENT under test — the staged tree for
pre-commit, HEAD for pre-push — not wall-clock. Re-running a gate over
unchanged content is a retry of the same attempt, not a new one, so it is
