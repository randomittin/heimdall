## 2026-08-27T08:01:53Z — [COMMUNICATION] fix(fallback): rank arm's self-pick on verified registry fields, not a false tools-denial

The previous ranking rested on a claim that is simply false: that `aihorde`
carries an explicit `tools` denial in `unsupportedParams`. I put that claim in
a code comment and in commit 70b487d's message after taking it from a subagent
report without checking it. `unsupportedParams` is a per-MODEL field resolved
through open-sse/config/providerRegistry.ts, which has NO aihorde entry at all,
so the lookup returns empty and aihorde's tool capability falls through to the
same optimistic heuristic as every other provider. No no-auth provider has a
provider-level tools denial. The correction is recorded in the code, next to
the sets it invalidated, rather than only in history.

The practical cost of that false premise: it demoted aihorde, so arm's default
self-pick became `auggie` -- which is isLocalCli:true and hasFree:false, i.e.
OmniRoute shells out to an `auggie` binary that must be installed AND have had
`auggie login` run on this machine. "OmniRoute stores no API key for it" is not
the same as "works keyless", and the happy path was defaulting to the one shape
of provider that cannot serve a keyless request at all. The ranking now reads
four named fields straight off noauth.ts (serviceKinds, isLocalCli, hasFree,
toolCalling) and the default pick returns to `aihorde` -- the same value as
before 70b487d, but now for a reason that is true.

An honesty boundary is recorded in the same block: `toolCalling` is unset for
most entries, and unset means OmniRoute's optimistic heuristic, NOT measured
support. Ranking first means "nothing in the registry says this is unusable",
never "measured capable".

## 2026-08-27T20:07:53Z — [COMMUNICATION] feat(fallback): make the route actually reach OmniRoute — base-url/token-file seam + precedence over headroom

`state=auto` was inert in the only place that mattered: nothing wired the gate's
verdict into a launch. `hmd fallback check` said ROUTE and `claude` still went to
api.anthropic.com, because headroom owns ANTHROPIC_BASE_URL and no code path ever
consulted the gate.

Two new fallback subcommands give `hmd route` a seam it cannot misread:

- `base-url` prints the endpoint on stdout IFF the verdict is ROUTE, and prints
  NOTHING to stdout on every other path — non-ROUTE, missing config, non-loopback
  endpoint, internal error. The caller does `url="$(... base-url)"` and exports what
  it gets, so a reason string or a traceback line leaking onto stdout would be
  exported as a base URL and point a live session at garbage. Reasons go to stderr.
- `token-file` prints the PATH of the gateway token, never its contents, and refuses
  a file with any group/world bits. OmniRoute enforces requireLogin on /v1/*, so a
  routed child without a token gets 401 and the fallback is decorative; the config
  records WHERE the credential lives, never the credential — the rule
  operator_key_env already follows.

The verdict is NOT re-derived: both share `_routing_decision`, which runs the same
preflight `check` runs. Two copies of a routing decision is how a wrapper starts
routing while the gate says REFUSE.

In heimdall-route, the fallback WINS over headroom when it says ROUTE, and the two
are mutually exclusive because both re-point the same variable. ROUTE only happens
because Claude capacity is gone — an uncompressed request that arrives beats a
compressed one that cannot. And headroom's compressed form reaches the provider
undecoded, so handing a weaker free-tier model a compressed prompt is the worst
moment to spend its comprehension on decompression. Chaining was rejected on
purpose: the chain pins HMD_HEADROOM_UPSTREAM to api.anthropic.com and refuses any
other destination, and that refusal is verified from the running process — widening
it would trade a measured security property for a compression saving on the path
where compression matters least.

On any launch NOT routed to the fallback, the gateway token is dropped from the
environment if and only if it byte-matches the token file, so a bearer credential
for a local gateway never rides along to Anthropic while an operator's real
Anthropic token in the same variable is left untouched.

--url and --status now answer for the fallback destination too — a shell function
built on `hmd route --url` must not point somewhere a real launch does not go.

The header's "It sets ONE variable on ONE child" claim was made false by this change
and is rewritten, not left standing: a header asserting a narrower blast radius than
the code has is worse than no header.

Verified end to end, not asserted: launch through `hmd route` in a repo with
state=auto and real session usage past threshold returned ROUTED_VIA_HMD at exit 0
with the fallback disclosure on stderr; OmniRoute call_logs show source_format=claude
translated to openai, provider opencode-zen, status 200. Tier-1 boundary holds —
provider_connections and call_logs both have 0 rows for claude/claude-web.

## 2026-08-27T20:37:21Z — [COMMUNICATION] feat(fallback): pin the model on a routed child — the last thing blocking unattended `auto`

`state=auto` was inert in practice, and not for the reason it looked like. The gate's
own preflight vetoed every unattended launch: anthropic_model_pinned FAILS when
ANTHROPIC_MODEL is unset, and ANTHROPIC_MODEL is unset in a normal session. So no
matter how exhausted the operator's Claude quota got, `auto` could only ever say
WAIT. The routing seam landed in 6de9093 and still could not fire.

The check's intent is sound and is kept: a bare `claude-*` id must never reach
OmniRoute, which has an explicit branch matching it to provider 'claude'. But the
check tested a proxy for that intent — "is ANTHROPIC_MODEL set" — when what actually
matters is "will this child emit a bare claude id". hmd can guarantee the latter
itself, so the check now passes when hmd will do the pinning:

- new `fallback_model` config field, EMPTY by default. Empty changes nothing: the
  check fails exactly as before. The feature is opt-in and default-off.
- `heimdall-fallback model` prints the id to pin, or nothing — the same stdout
  contract base-url has, because `hmd route` reads it in a command substitution and
  exports the result as ANTHROPIC_MODEL. A reason string on stdout would become the
  model id of a live session.
- heimdall-route exports it on the fallback path only, and only when the operator has
  not set ANTHROPIC_MODEL themselves.

An operator-set ANTHROPIC_MODEL always outranks the configured one, including when
the operator's value is the unsafe one. hmd reports that rather than silently
substituting its own id — a tool that quietly overrides an explicit choice is worse
than one that refuses.

Closes a real hole in the same check while here. It tested `"/" not in model`, which
accepts `claude/sonnet` and `claude-web/anything` — the provider prefix naming the
Tier-1 subscription EXPLICITLY passed the check that exists to keep Tier-1 out.
tier1_credential_absent is the primary defense and still held, but a second line of
defense that admits the exact id it defends against is not one. Now the provider
SEGMENT is split on the first '/' and compared exactly, case-insensitively, so
`anthropic/claude-3-5-sonnet` (a paid API key, a different thing entirely) is still
accepted while `claude/*` is not. Matching 'claude' as a substring would have broken
that legitimate id, which is why the comparison is on the segment.

Verified end to end with no ANTHROPIC_MODEL in the environment at all: `check` ->
VERDICT: ROUTE (structurally impossible before this commit); launch through
`hmd route` -> exit 0, stderr carries both the fallback disclosure and
`· fallback: pinned ANTHROPIC_MODEL=oc/big-pickle`; OmniRoute call_logs show provider
opencode, status 200, cache_source=upstream (nothing served from cache). Tier-1
boundary unchanged: 0 rows in provider_connections and call_logs for claude/claude-web.

Two corrections to earlier claims in this work, recorded so they are not re-derived:
the operator token budget is NOT required for the real-usage signal (source=real with
budget_configured=false), and session_usage reporting "tracking not configured" was
not a defect — freshness is judged by resets_at, so an expired window is correctly
absent rather than a falsely low reading.
