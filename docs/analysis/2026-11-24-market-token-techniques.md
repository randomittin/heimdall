## 1. Can a hook replace a built-in tool's output? YES (tested)

- Docs (https://code.claude.com/docs/en/hooks, PostToolUse decision control): `hookSpecificOutput.updatedToolOutput` "replaces the tool's output with the provided value before it is sent to Claude. The value must match the tool's output shape." Works for built-in AND MCP tools; `updatedMCPToolOutput` is the MCP-only legacy field. A shape mismatch on a built-in is silently ignored (original used). `PostToolUseFailure` cannot rewrite. `PostToolBatch` can only add `additionalContext`. OTel telemetry keeps the original.
- **MEAS, local probe on 2.1.331 (appendix P1-P3):** Bash `{stdout,stderr,interrupted,isImage}` replacement reached the model (it answered with the rewritten text). Read replacement in the shape `{"type":"text","file":{filePath,content,numLines,startLine,totalLines}}` also reached the model. The session transcript stores the REWRITTEN `tool_result`. So the rewrite is real, persistent in history, and cache-safe (it happens at insertion; the prefix is never edited later).
- Contrary evidence, now stale: issue https://github.com/anthropics/claude-code/issues/54196 (v2.1.121-123: built-in rewrite dropped; closed "not planned" by the stale bot, no fix linked). Works on 2.1.331; pin a probe test (appendix P1) so a regression goes red.
- Other levers: `PreToolUse` `updatedInput` rewrites the whole input of any built-in (e.g. add `limit` to a Read). `additionalContext` (cap 10,000 chars) adds, never replaces. A rewrite cannot reach text Claude Code injects as user messages: the 1,152 background-agent `task-notification`s are such text (2.75M chars, about the same as ALL main-thread tool results, section 2), so hooks cannot shrink them. `SubagentStop` input has `last_assistant_message`, `agent_id`, `agent_transcript_path`, and `decision:"block"` + `reason` keeps the subagent running (enforcement path for a report-length rule). `SubagentHandback` (report delivered via a tool a PreToolUse hook can rewrite) exists only in auto mode: 0 uses in this corpus (MEAS), not usable here.
- Cannot do with hooks: retroactive observation masking (editing OLD tool results). It would also bust the cache from the edit point. Native API analogue `clear_tool_uses` is not exposed in Claude Code (request: https://github.com/anthropics/claude-code/issues/106802, open when searched, UNVERIFIED now).
- UNVERIFIED: whether plugin PostToolUse hooks rewrite output for tool calls made INSIDE subagents (hmd's own PostToolUse hooks do run there, but I did not probe the rewrite). Probe before building (appendix P4).

## 4. Top 5 buildable gaps (ranked by DERIVED/INF saving, then effort)

Shared mechanism for 1, 3, 4: one fail-open `bin/heimdall-posttool-shrink` (stdin JSON, prints `updatedToolOutput` JSON or nothing), registered as ONE PostToolUse entry matcher `Read|Bash|Grep|WebFetch` in `hooks/hooks.json` (precedent: the Bash PostToolUse entry that calls `edit-tracker`, same file; `hmd_hook_enabled` toggle pattern from `bin/lib/hook-enabled.sh`). Build #1 first, in its own wave; #3 and #4 touch the same script, so sequence them (same-file rule). Hooks fail open: any error prints nothing = original output. No full-suite run; each ships one `test/<name>.test.sh`.

**1. Unchanged re-read stub (Cline/Roo precedent). S-M, DERIVED $21, up to $45 INF.**
- State: `${HEIMDALL_HOME:-.heimdall}/shrink/<sha1(transcript_path)>.json`, map `path|offset|limit -> {mtime_ns,size,sha256_first_64K,tool_use_id}`. `transcript_path` differs per subagent, so each agent has its own state (UNVERIFIED that it does inside subagents: probe P4).
- On PostToolUse Read: stat the file. If an entry exists with equal `path,offset,limit,mtime_ns,size,hash` and the prior read is still in context: return `updatedToolOutput` = same shape with `content` = `[hmd: unchanged since your Read #<n> (sha256 <8>); output omitted, see that result]` and `numLines:1`. Else record and print nothing. PostToolUse Write/Edit/MultiEdit on the path deletes its entries (an edit makes the next read legit). PreCompact hook (`hooks/hooks.json` already has one) deletes the state file, since the first read left context.
- Test `test/shrink-reread.test.sh`: (a) read twice, 2nd output is the stub; (b) edit between, 2nd is full; (c) different offset, full; (d) corrupt state file, no output (fail open); (e) the probe P3 shape is accepted by the real CLI (skip when `claude` is absent).
- Falsify: rerun `tr4.py` on the next 30 days of subagent files: identical re-read chars < 5% of Read chars (now 44.2%).

**2. Subagent final-report gate. S, $20-25 INF (11-22 lever 5, not a new idea; here is the hook form).**
- `SubagentStop` hook, matcher = the hmd agent types: if `len(last_assistant_message) > 1500` and `stop_hook_active` is false, write the full text to `.planning/reports/<agent_id>.md` and return `decision:"block"`, `reason:"Report is N chars. It is saved at .planning/reports/<agent_id>.md. Reply with <=1,500 chars: verdict, files changed, path above."` The subagent spends one short turn; `stop_hook_active` prevents a loop. Pair with the one-line clause in `agents/coder.md`, `architect.md`, `test-runner.md`, `docs-writer.md` so most agents comply the first time and the hook is the backstop.
- Why a hook and not a rewrite: 1,152 reports arrive as `task-notification` text (hooks cannot rewrite it); `SubagentHandback` is auto-mode-only.
- Cost of the gate: one extra subagent turn at cache-read price (about 50K tokens x $0.2/MTok = $0.01) for the share of reports over the cap. Test `test/subagent-report-gate.test.sh` (long report blocks once; short passes; second stop passes). Falsify: next 100 notifications mean chars < 1,600 (11-22 `rep5` query).

**3. Read of a big, unsliced file returns outline + head (Aider repo map / Roo signatures). M, INF $10-25 incremental over #1.**
- In `bin/heimdall-posttool-shrink`, Read with no `offset/limit`, source file > 400 lines or > 16K chars, tool_response shape per P3: replace `content` with the first 120 lines plus `bin/heimdall-graph outline <file>` output (symbol, line range) plus `[hmd: file has N lines; showing 120. Use offset/limit or heimdall-graph def <symbol>]`. Skip: `.md`, `.json`, `*.test.*`, a file the agent just Edited, a path under `evals/` or `fixtures/`. Allow-through when the same path was already partly read with a slice (the model chose to slice).
- `heimdall-graph outline` already exists; fail open when the index is stale or the language is unsupported (the lib degrades gracefully: `bin/heimdall-ast` header).
- Risk and falsifier: the model may re-read in slices and give back the saving. Falsify: subagent Read chars per agent drop >= 20% AND coder verifier pass rate does not fall (use the `evals/effort-ab` harness style, 10 tasks x 2 arms; a quality ceiling effect applies, same limit as 11-23 section 4).

**4. Spill and context-adaptive cap for Bash/Grep/WebFetch (Cursor, Codex, Gemini, Kilo). S then M, INF <= $10-20.**
- Step S, no code: operator env `BASH_MAX_OUTPUT_LENGTH=15000` and `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS=10000` (same `env` block pattern as the docs example). Cut is at the tail only; spill adds recoverability.
- Step M: PostToolUse Bash/Grep/WebFetch, if `stdout` > threshold: write the full text to `.heimdall/spill/<session>/<tool_use_id>.txt` (0600, swept by `bin/heimdall-gc`), return the first 3K + last 2K chars + `[hmd: N chars; full output at <path>; grep/sed -n it]`, keep `stderr`, `interrupted`, exit info whole. Threshold from the ctx record `heimdall-ctx-meter` already publishes: 30K chars below 150K tokens, 8K at 150-300K, 3K above 300K (reuse the meter's existing ceiling; no new threshold).
- Secrets: the spill file holds raw output; keep the existing `secret-read-guard` path rules, `chmod 600`, never log contents. Test `test/shrink-spill.test.sh`. Falsify: share of Bash results > 8K chars in the next 30 days of main transcripts (now 23 of 3,795).

**5. Plan-slice enforcement for coders. S, INF $5-10 (overlaps #1).**
- 11-22 doc: plan files read whole by 76, 22, 17 and 13 coders (12.5% of Read chars). `bin/heimdall-brief build` should emit the task's line range in the plan (`Read <plan> offset=A limit=B`) in the spawn brief, and #1's hook returns a slice of any unsliced Read of `.planning/PLAN-*.md` when the agent's spawn prompt carries a task id. Hook branch lives in the same script as #1, so build it after #1.
- Falsify: Read chars of `.planning/PLAN-*` per coder < 3K chars (11-22 `sub.py` method).

Combined (non-additive; #1, #3, #5 overlap): about $40-70 = 2-4% of $1,805 (INF). That is small next to 11-22 lever 1 ($470, DERIVED). Market tool-output techniques mostly target big, fresh tool outputs on the main thread; hmd's main thread has few (section 2). The honest finding: the highest-yield gaps remain the compaction window and the cold-cache return, which other harnesses corroborate (rows 5-6), and the rest is subagent Read hygiene.

## 5. Red flags

- Rewriting tool output changes what the agent believes it saw. Every stub must say it is a stub and how to get the full text; never silently drop content. A model that distrusts a partial Read may re-read (rebound).
- Hook rewrite on subagent tool calls is UNVERIFIED (P4). If it does not fire there, #1, #3, #5 lose their subagent target and the table's $ collapses to about zero (the main thread has 4 Reads).
- Subagent tool-result sizes come from 171 files of one big session on one machine (n=1 operator); re-read share depends on this operator's agent templates.
- Vendor numbers (Cursor 46.9%, OpenHands 2x, Anthropic 84%, Augment 33/41%, Windsurf 20x) are vendor-run and uncontrolled for quality; none was used as an hmd estimate.
- `updatedToolOutput` was broken in 2.1.121-123 and may regress; P1 as a unit test catches it.
