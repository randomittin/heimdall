## Interpretation (correct me)

1. **Profile, not removal.** `profile = lean | full`. Existing installs (setup marker present / `skills-config.json` `grandfathered: true` / install dir already a git clone) are `full` forever unless they run `hmd lean on`. Only fresh installs default `lean`. `full` must be byte-identical to today (INV-L1).
2. **Core (stays, always):** every `core` guardrail (24 in `guardrails.manifest.json`), all hooks, `bin/`, `modules/` manifests, `hmd` orchestrator + 16 agents, `skills/heimdall`, `skills.manifest.json` registry + consent + lock, `release/` signing material, `evals/oracles` + whatever `T0.2` proves reachable.
3. **On-demand (lean):** `skills/{stacks,designmatch,mac-deep-clean,system-health}`, `commands/designmatch.md`, and the non-runtime directories. Mechanism = `git sparse-checkout` on the install clone (a plain depth-1 clone keeps every object locally): bundled fallback stays real and offline, "install" = `sparse-checkout add <path>` + lock row, takes effect next session like any plugin. `hmd skills install stacks` etc. use the existing M1 consent path.
4. **Pack package (spec Stage 2):** `@runhmd/stacks` is built from the in-tree files by `bin/heimdall-pack-build`; resolver prefers an installed pack whose hash matches the lock, else the bundled copy, silently. Publishing to skills.sh/npm is NOT done here (operator action).
5. **Prompt:** lean profile uses an added `agents/heimdall-lean.md` (core ~24 KB + pointers to on-demand reference reads of sections 2/4/5); `agents/heimdall.md` is untouched. Selecting it needs a settings override whose precedence over plugin `settings.json` is UNVERIFIED (spike S2). If it cannot work, W4 becomes a doc-only recommendation and the plan still ships the disk win.
6. **Marketplace install path:** `install_hmd_plugin` (`install.sh:939`) registers hmd as a Claude Code plugin, and Claude copies the marketplace source (whole repo) into its own plugin cache. Sparse checkout does not reach that copy. Spike S1 decides whether a dist subtree/branch source is possible. Until S1 lands, the lean disk win is claimed for `$PLUGIN_DIR` only (unmeasured how much of total install it is).

## Ledger (wave-0 artifact, T0.3): `.planning/lean-core/INVARIANTS.md`, listed under Read first for EVERY task after W0

- INV-L1: profile `full` => every injected byte (agents, commands, skills frontmatter, hook stdout) and the file tree equal today's (hash in `evals/lean/context-baseline.json`).
- INV-L2: profile is derived once: marker/dir present at first lean-aware run => `full`; never flips without `hmd lean on|off`.
- INV-L3: no `core` guardrail, no hook, no `bin/` file is removed or gated by profile.
- INV-L4: on-demand add never needs network (objects local) and writes one lock row with reason.
- INV-L5: pack with hash mismatch or missing => bundled copy, silent, never an error; a bundled copy is never deleted.
- INV-L6: `hmd lean off` restores the full tree (`sparse-checkout disable`), idempotent.
- INV-L7: an upgrade (`install.sh` re-run) re-applies the recorded profile, never resets it.
The ledger has no teeth alone: T5.1 differential and T0.1 budget are the gates.
