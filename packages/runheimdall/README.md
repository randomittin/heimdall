# runhmd (hmd): a verification gate for AI coding agents

**hmd is a command-line test gate for AI coding agents that runs as git pre-commit and pre-push hooks.** runhmd makes your coding agent's work pass a test it didn't write — and proves that test can fail — before the push lands.

`hmd` is the one CLI; Heimdall is the engine underneath ([NAMING.md](NAMING.md)). One prompt in, a gated, receipted change out. The gate is a plain git hook that `hmd init` installs, so it holds in any git repo, whichever agent or person made the commit. Your agent's own tests are a claim; the oracle it wires is external, and is first shown to go red on a planted defect before its green is trusted.

Works with, today: Claude Code and Cursor (installing hmd needs Claude Code 1.0+, git and jq: [prerequisites](docs/INSTALL.md#path-1--the-one-liner)).

## Why

An AI coding agent writes the change and the tests that approve it, so "tests pass" is the agent's own claim, and a test that cannot fail proves nothing. hmd moves the judgment outside the agent:

- **The check is external.** An oracle is a reference the implementing agent never sees ([oracle registry](evals/oracles/README.md)), not the agent's own tests.
- **The check is shown able to fail first.** Planted defects ("mutants") must turn a gate red, or `bin/falsify` exits non-zero ([run it yourself](#check-the-proof-yourself)).
- **The check sits in git.** `hmd init` installs pre-commit and pre-push hooks; a red gate exits non-zero and names what failed, so the commit or push does not go through.
- **A human does the merge.** `test/no-auto-merge.test.sh` fails if any shipped code path merges, pushes or deploys without a classified human trigger.

## What `hmd attack` does

`hmd attack <path>` asks "can I break this?" and answers **PROVEN** or **DENIED**, with a counterexample.

- **Target:** a directory that declares its attack surface in `runhmd.attack.json`, or a single `.mjs` module. A directory that declares nothing exits 2: a verdict over nothing would be a false green. `--diff` and PR URLs are not supported in this build.
- **Engine:** deterministic and offline: no model, no network, $0.00. The target runs in an ephemeral temp dir, in a scrubbed environment.
- **Output:** the card above; `--json` prints the canonical `runhmd.verdict/1` document; `--out DIR` writes the evidence.
- **Exit codes:** 0 PROVEN · 1 DENIED · 2 usage/config · 3 consent required (non-TTY without `--yes`) · 4 budget cap · 5 infrastructure.
- **Receipts:** `--receipt` issues a signed `runhmd.receipt/1`, stored locally and checked with `hmd receipt verify`. The hosted `runhmd.dev` service is not built yet ([docs/RECEIPTS.md](docs/RECEIPTS.md)).

`hmd demo` is dry by default: it scaffolds a full-stack task into `./heimdall-demo-app` and prints the next step; it executes nothing until you add `--run`.

## How hmd differs from an agent grading its own work

| | The agent's own "tests pass" | hmd |
|---|---|---|
| **Who wrote the check** | The agent that wrote the change | An oracle: a reference the implementing agent never sees ([`evals/oracles/README.md`](evals/oracles/README.md)) |
| **Shown able to fail first?** | A green run does not show the test could have gone red | The hooks run `bin/falsify <domain> --assert-score 1.0` for each oracle that ships planted-defect fixtures, and a gate that cannot go red is denied ([`bin/heimdall-gate-run`](bin/heimdall-gate-run)) |
| **What stops a bad change** | The agent's report that it passed | Git pre-commit and pre-push hooks that exit non-zero and print what failed ([`bin/heimdall-init`](bin/heimdall-init)) |
| **Where the verdict comes from** | The agent's explanation | Artifacts on disk, not the agent's explanation; the last verdict is `.heimdall/verdict.json` (`hmd verdict`) |

The left column is a pattern, not a named product: this repository holds no benchmark against any named tool, so none is claimed. Every cell in the right column names the file or command that shows it.

**What the installer writes outside the repo** (measured from a real run against a throwaway `$HOME`; no sudo, idempotent, `hmd uninstall` reverses all of it):

- `~/.heimdall/`, `~/.local/bin/hmd` and `~/.local/bin/heimdall`: a full clone of this repo, and symlinks into it.
- `~/.claude/settings.json`: a `statusLine` and `subagentStatusLine`, and the plugin under `enabledPlugins` / `extraKnownMarketplaces` (honors `$CLAUDE_CONFIG_DIR`; never clobbers a `statusLine` you set).
- `~/.zshrc` / `~/.bashrc` / `~/.profile`: one appended `export PATH=…` line, only when `~/.local/bin` is not already on `PATH`.
- macOS only: a nightly 03:00 LaunchAgent, `~/Library/LaunchAgents/com.heimdall.dream.plist` (opt out with `HEIMDALL_NO_DREAM_SCHEDULE=1`).
- `~/.heimdall/team.json`: an auto-minted solo team secret, a bearer capability: treat it like a credential.

**Headroom, an optional local proxy that can read your prompts, is off by default.** A fresh install never installs it, loads no launchd job for it and never points `ANTHROPIC_BASE_URL` at it; `hmd modules status headroom` reports `NOT ATTEMPTED` until you run `hmd headroom on`. That command runs `hmd modules add headroom` if the module is absent (a remote code install with no digest verified) and starts nothing itself: the proxy starts on the first launch you route through `hmd route claude` or `hmd wrap claude`. `hmd headroom off` undoes it (`hmd headroom off --next-session` from inside a routed session), and an install that already has the module keeps it until you run that. Disclosure in full: [docs/INSTALL.md](docs/INSTALL.md) and [SECURITY.md](SECURITY.md#the-headroom-proxy--a-local-process-that-reads-your-prompts).

## Check the proof yourself

No trust required (~1 min, network-free after the clone):

```bash
git clone https://github.com/randomittin/heimdall && cd heimdall
bin/falsify exchange-lob --assert-score 1.0   # every mutant must turn the gate RED, or exit non-zero
bin/falsify emulator-gb  --assert-score 1.0
```

Real output from this tree (2026-09-19), last lines of each run — a survived mutant would print `REJECTED` and fail the assert:

```text

ASSERT PASS: score 1.0000 >= target 1.0 (golden passed, no mutant survived)

SCORE: 3/3 = 1.0000 (golden passing)
ASSERT PASS: score 1.0000 >= target 1.0 (golden passed, no mutant survived)
```

## FAQ

### What is hmd (runhmd), and how do runhmd, hmd and Heimdall relate?

hmd is a command-line test gate for AI coding agents: it runs as git pre-commit and pre-push hooks and blocks a change until it passes a check the agent did not write. **runhmd** is the product and the npm package, **`hmd`** is the one CLI you type, and **Heimdall** is the engine underneath, the repository (`randomittin/heimdall`) and the plugin name ([NAMING.md](NAMING.md)). It is MIT-licensed ([LICENSE](LICENSE)). Other, unrelated software is also called Heimdall; this is the verification gate described here.

### How do I stop an AI coding agent from pushing failing code?

Put a gate between the agent and `git push` that the agent cannot pass by saying it passed. With hmd, run `hmd init` in the repo: it installs git pre-commit and pre-push hooks (`core.hooksPath=.heimdall/hooks`; hooks you already have are chained, not replaced) that run the repo's gates through `bin/heimdall-gate-run`. A red gate exits non-zero and prints a `BIFRÖST` block naming what failed, so the commit or push does not go through. Limits, stated plainly:

- A repo with no gate configured passes quietly (the stub scan of the staged diff still runs at commit), so the gate is only as strong as the oracles you wire.
- `HMD_SKIP=1` skips the hooks and writes an unproven-merge record to `.heimdall/receipts/unproven.log`.
- `git push --no-verify` skips any git hook, hmd's included. Where the host lets hmd see an agent's commands before they run, hmd also runs its push checks there, and that flag does not skip them.

### How do I verify code an AI agent wrote?

Check it against something the agent did not write. `hmd attack <path>` tries to break a target that declares its attack surface in `runhmd.attack.json` (or a single `.mjs` module) and answers PROVEN or DENIED with a counterexample; it is deterministic and offline, with no model in the loop. `hmd prove` answers whether every gate in a repo passes and has been shown to fail first, and `hmd verdict` prints the repo's last gate result and why. After `hmd init`, the repo's configured gates also run on every commit and push.

### What is a "false green", and how does hmd catch one?

A false green is a passing check that could not have failed, such as a test that asserts nothing the code can break. hmd trusts a gate only after planted defects ("mutants") have turned it red: `bin/falsify <domain> --assert-score 1.0` exits non-zero if any mutant survives. In this repository's own 2026-06-11 spike on a limit-order-book matcher (same model, with and without hmd's process; the file uses its earlier name, superx), the run without it shipped a concurrency test that cannot fail, and the run with it caught the race at seed 1, trade index 0. The table keeps the rows where nothing differed too: [`evals/flagship/STATUS.md`](evals/flagship/STATUS.md).

### How do I know hmd's own gates can fail?

Run the proof yourself, in about a minute and without network after the clone: `bin/falsify exchange-lob --assert-score 1.0` and `bin/falsify emulator-gb --assert-score 1.0` exit non-zero unless every planted defect turns the gate red, and their last recorded runs caught 6 of 6 and 3 of 3 ([Check the proof yourself](#check-the-proof-yourself)). `bin/corpus run` replays 13 recorded cases through the same gates, with a last recorded result of 13/13, and its dip log records a real red run and the recovery ([`evals/corpus/CORPUS-STATUS.md`](evals/corpus/CORPUS-STATUS.md)).

### Which AI coding agents does hmd work with?

Works with, today: Claude Code and Cursor (installing hmd needs Claude Code 1.0+, git and jq: [prerequisites](docs/INSTALL.md#path-1--the-one-liner)).

The gate is a plain git hook, so after `hmd init` it checks every commit and push in the repo, whichever agent or person made it, and `hmd init` also writes an `AGENTS.md` block, the file coding agents read at session start, saying the repo is gated. What differs by host is the extras: live write-time stub blocking, session automation and sub-agent orchestration need hooks that not every host provides ([the full list](docs/ARCHITECTURE.md#what-you-dont-get-under-cursor)). How each host is gated: [Architecture](docs/ARCHITECTURE.md#also-gates-cursor-cli).

### Does hmd send my code anywhere?

Gates run 100% locally. Your code never leaves your machine unless you pair a phone with hmd app connect. Some features do reach the network, each scoped and each listed field by field in [DATA.md](DATA.md). Among them: team presence sends {handle, verdict, current filename}, never code or file contents (`hmd presence sever` stops it); the updater checks GitHub Releases (`HEIMDALL_NO_AUTOUPDATE=1` stops it); phone pairing registers a six-minute code with a relay (`HMD_PAIR_WINDOW=0` stops it); and `rr` sends what you give it, only when you run it. The scoped claims are under [Your code stays yours](#your-code-stays-yours).

### Can hmd merge or deploy for me?

Not on its own: a human always gates the merge. The cloud bot `rr` opens its pull request on a `heimdall/*` branch as a scoped GitHub App, never as you and never on `main`, and it never self-merges. `test/no-auto-merge.test.sh` fails if any shipped code path merges, pushes or deploys without a classified human trigger, and prints the human-run commands it accepts (for example `hmd land`). More: [Get a bot PR on your repo](#get-a-bot-pr-on-your-repo).

## Your code stays yours

**Network posture is default-ON.** Team presence and the cloud features reach the control plane as soon as you use them: a signed heartbeat carrying your handle, verdict, and current filename — scoped to your team, never your code or file contents. That is a feature, and it is on until you switch it off. `hmd presence sever` gives zero egress. Field-by-field contract: [DATA.md](DATA.md). The precisely scoped claims are below.

Gates run 100% locally. Your code never leaves your machine unless you pair a phone with hmd app connect.

Team presence is a feature you can see and switch off: it sends {handle, verdict, current filename} — never code, never file contents — to your team's endpoint. hmd presence off makes you invisible; hmd presence on --no-files hides filenames.

Telemetry is specified, minimal, and yours to kill: DATA.md documents every field. hmd telemetry off. hmd telemetry purge deletes the local spool — nothing is transmitted in this release.

Auto-update checks GitHub Releases for new signed versions. HEIMDALL_NO_AUTOUPDATE=1 (or ~/.heimdall/no-autoupdate) disables it.

`rr` sends on purpose, and only when you run it: your BYO Claude credential (write-only), your GitHub App installation id, and the literal task text you typed — because that text is the job. It never uploads your working tree; the worker clones your repo from GitHub.

The phone companion is on by default for pairing (a session start in any repo registers a six-minute code with the relay, and nothing of your session is sent until a phone pairs; HMD_PAIR_WINDOW=0 turns that off for the machine, and hmd app disconnect or hmd app connect --no-code for one repo): once a phone is paired, your session state, and any diff you open on the phone, travel end-to-end sealed through a relay that sees only ciphertext; push notifications send short scrubbed text to Expo (HMD_PUSH=0 turns them off); pairing by code sends your gh auth token to the relay once for each code registered for a phone to claim (a session start of a repo with no phone paired, hmd app connect, or hmd app add-device), not on a timer and never while gh is signed out (--no-code pairs by QR instead and sends no token).

Full data contract and every field collected: [DATA.md](DATA.md).

## Get a bot PR on your repo

`rr` is the same gate, run in the cloud: a bot that fixes your GitHub issues and opens a PR whose fix has already passed a check the agent never wrote. The bot opens it on a `heimdall/*` branch **as a scoped GitHub App** — never as you, never on `main`, and it never self-merges. A human always gates the merge: `test/no-auto-merge.test.sh` fails if any shipped code path merges, pushes or deploys without a classified human trigger. Agent instructions count as code paths: the maintainer guide and the incident responder prepare a release or a fix and stop for the operator to run it, and the gate fails if that wording regresses, so it accepts no known gaps there. On every run it prints what it does accept: the human-run executables (for example `hmd land` and the release and deploy scripts) whose merge, push or deploy step has no in-code confirmation, because a human typing the command is the trigger, and it checks that no unattended surface names them. Setup, the isolation oracle and the bring-up notes: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#get-a-bot-pr-on-your-repo).

## Running on your own work

`heimdall --auto "<task>"` runs Claude Code's auto permission mode (a background safety classifier). With no flag, `heimdall` launches Claude Code with `--dangerously-skip-permissions` (full autonomy): pass `--auto` first for the safer opt-in.
